# 设备故障后批量计划重优化：工程资格门槛核查

日期：2026-09-25。状态：**未通过**。这是源文件与环境核查，不是算法实验；未安装、未训练、未生成故障数据、未宣称复现。

## 门槛逐项

| 必需件 | 已核查到的事实 | 裁决 |
|---|---|---|
| 可验证的同一问题模型 | Lerouge 等的论文给出 MILP 式 (1.1)–(1.15)、故障/修复定义和附录伪代码；未定位到作者可运行的模型源码与测试资产。 | 数学规格有，**可运行且已验证的实现没有** |
| 同一分布的实例 | 论文描述自行生成 500 个 2–4 机器、30–40 产品、30 时段实例；未定位到这些实例的下载入口或生成代码。 | **没有可核验实例文件** |
| 高质量可行名义解 | 论文逐实例用 6000 Gurobi work units 求名义计划；未定位到逐变量计划文件。 | **没有**；仅凭一个目标值不能修复计划 |
| 故障后的正确修复接口 | 论文给出了取消故障机器生产、处理被打断 carry-over、重算库存/失销的伪代码；未定位到可运行实现与单测。 | **没有** |
| 本机求解器 | PATH 中无 SCIP/Gurobi/CBC/HiGHS 命令；有 Octave 附带 `glpsol`。现有 Python 可调用 SciPy 1.18.1 的 `milp`，但没有 PySCIPOpt/GurobiPy/OR-Tools/PuLP/highspy。 | 能做不同求解器的原型，**不是现成的论文修复环境** |

一手来源：[Lerouge 等，模型、修复、实验设置](https://arxiv.org/pdf/2605.27339)。论文明确假设高质量可行名义解，实验中用 6000 work units 逐实例生成；短期重优化给 10 work units。数学式并不自动提供可执行的模型、求解器 warm start 和已验证修复。

## 另一公开仓库为什么不能填补缺口

[clsp_pm_study](https://github.com/lost-ufpb/clsp_pm_study) 的 GitHub 递归树核查为 3161 项（未截断），其中 2921 个 `.dat`、32 个 `.csv`；没有 `.py/.jl/.mps/.lp/.sol/.mst` 文件。README 说明它提供 Toledo–Armentano 静态并行机批量规划实例及目标值/界等详细结果。抽查 `MIP_600` CSV 仅有 `Instance;NI;NM;NT;LB;UB;gap;status;total_time`，不是逐变量生产计划。抽查一个实例文件可见 `12 12`、`2` 等静态参数，但没有故障状态与名义计划。

因此，不能把该仓库的 UB 充当 Lerouge 问题的名义解；也不能把另一种模型/维度的静态实例称为作者 500 个故障重优化实例。若用它构造新研究基准，必须从模型、名义解、故障、修复到验证全部重新建立，并明确标为**新生成基准**。

## 当前裁决

贴文设定的前置门槛要求先有“可验证模型＋可行名义解＋正确修复接口”。目前只取得论文中的数学与伪代码规格，**未达到开跑 48 状态、2/10 秒邻域比较的资格**。按约定到此停止，不把两天资格验证扩张成无期限环境开发，不先运行 GRL 或轻量模型。

可解除门槛的最短输入：作者或用户提供同一问题的可运行模型/实例/逐变量名义解与修复代码（或等价经验证资产）。若决定自主重建，则是另立的实现/基准工程：需要先定义求解器、实现模型并逐约束验解，再构建可行名义解与故障修复，不能直接沿用本文的性能数字。
