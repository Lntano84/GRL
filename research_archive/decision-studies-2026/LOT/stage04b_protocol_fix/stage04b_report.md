## A. 修正的记录与返回接口

### A.1 Stage 04 的错误

约定是"始终返回修复解与求解器可行解中**更好的一个**"，但 Stage 04 的实现只在**没有 incumbent** 时回退。离线复核确认：**288 次计时运行中 114 次的返回成本高于同一状态已有的修复解**，其中 20 秒运行 25/96、**large 的 FULL@20 为 8/8**。这不是热启动问题——即使求解器完全不支持热启动，外部保留更优计划也必须成立。

### A.2 现在的接口

每次运行分别保存 `raw_solver_solution`（可为空）、`selected_solution`、`selected_source`（`solver`/`repair`），规则固定为

$$J_{\mathrm{out}}=\min\big(J_r,\ J_{\mathrm{valid\ incumbent}}\big)$$

**两个候选都独立检查**四项：原模型约束、相对修复解的稳定性预算、该方法的固定条件、重算成本。无效 incumbent 记为**错误**；求解器报告不可行而修复解是可行见证时也记为**错误**。

`lsp_select.py` 是这条规则的独立模块，`stage04b_selection_test.py` 用 5 个人工用例覆盖它（不调用求解器）：

| 用例 | 结果 |
|---|---|
| A 无 incumbent | 保留修复解，`reason=no_incumbent`，0 错误 |
| B incumbent 更差（90 vs 4） | 保留修复解，`reason=incumbent_worse_or_tied`，0 错误 |
| C incumbent 更好 | 采用 incumbent，`reason=incumbent_better`，0 错误 |
| D incumbent 违反模型（activation） | 保留修复解，**1 个错误**：`INVALID INCUMBENT` |
| E 求解器报不可行但修复解是见证 | 保留修复解，**1 个错误**：协议错误 |

用例 C 需要"参考解不如 incumbent"，因此把角色对调：用带人工限制的可行解当参考（成本 62），用无限制最优（成本 4）当 incumbent。

## C. 补齐的修复测试

修复器单独版本化为 `lsp_repair3`，并按你的指示改正了**用错约束**的地方：原代码用 $X_t+X_{t+1}\ge m(Y_t+Y_{t+1})$，而主模型是 $X_t+X_{t+1}\ge mZ_t$。前者更强，会取消合法延续；现改为原约束。**本次复测仍使用 Stage 04 已验解的修复计划**，所以比较起点没有同时改变。

### R1：原 F 参数，双机延续同时被打断（**42 得到证实**）

Stage 04 的 R1 用了需求 $(1,1)$ 与名义 $Y=(1,1),Z=(0,0)$，**没有被打断的延续**，因此没有检验原定情形。现在改用原 F 精确参数：需求 $(1,2)$、容量 $(2,2)$、名义 $X=(1,2),Y=(1,0),Z=(1,0)$，两机第 1 期同时停机。

| 项 | 结果 |
|---|---|
| 修复成本 | **42**（与预期一致） |
| 账目 | 每机 $10$（第1期损失）$+\,10$（第2期只能产 $m=1$，再损 1）$+\,1$（恢复换型）$=21$；两机 $=42$ |
| 恢复事件数 | **2**，位于 `(机器0, t2, 产品0)` 与 `(机器1, t2, 产品1)` |
| 机器编号互换 | 成本不变 42 |
| 独立验解 | 通过，最大违反 0.0e+00 |

### R2：零产量换型位于**实际恢复期**

原 R2 把该位置放在恢复期之外，没有直接覆盖旧代码"清除 $X=0$ 处的 $Y,Z$"的风险。现在机器 0 第 1 期停机（恢复期 $=t_2$），脆弱位置就在 $t_2$，同机产品 1 因停机需要恢复决定。

设计上受两条已有约束限制，已记录在设计注释中：**(1.7) 禁止连续延续**，故该位置的前一期 $Z$ 必须为 0；**(1.9)** 在 $Y=Z=1$ 时给出 $X\ge0$，故 $X=0$ 合法。结果：位置与下一期生产**均保留**，产品 1 的取消照常发生，独立验解通过。

## F. 修正后的判断

**验收全部达成**：32 次运行的最终输出均不劣于已有修复解；64 个计划（选中 + 原始）全部可重读验证，最大违反 0.0e+00；计时口径一致。

**按你给的三种原因分开陈述：**

1. **输出协议错误** —— 已修正并验证：32/32 最终输出不劣于已有修复解，接口缺口（C9）也已补上。它对 Stage 04 大档异常的影响**很大但未被单独量化**，因为两轮的参照与状态集不同（C7）。

3. **名义解质量 / MIP 热启动** —— 本轮未触动。large 的**名义解仍是 Stage 04 的**（其 MIP gap 平均 66.3%，但**该数字只说明最优性未证明，不能推断名义解实际很差**，见 C8），且**始终没有 MIP start**（`scipy.optimize.milp` 无此参数，已核实）。

**因此仍不能据大档排名决定研究路线。** 下一步真正需要哪一种（热启动、更好的名义解、或变量选择研究），需要在**同口径**（同一状态集、同一参照）下重跑修正后的协议——这正是 Stage 05 要做的事：固定这 8 个状态，让冷、热两组都使用同一个 `highspy` 版本与同一初始解，直接检验"完整求解器收到 MIP start 后，限制变量还剩多少优势"。
