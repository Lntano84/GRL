# GRID81：新场景确认与门控消融

本轮只落实用户确认的两个优先事项：检查当前最终方法在新场景上的表现，以及检查条件核查的识别价值。模型、阈值、控制器和候选排序保持不变，不新增训练。

## 一、新场景从哪里来

现有官方2035数据的52个周日期家族都已在开发或教师运行中出现，本轮不把这些日期的另一个变体称为新日期。使用官方Chronix2Grid 1.2.0.post1生成六个2036场景：1月7日、3月3日、5月5日、7月7日、9月1日、11月3日，生成种子固定20261016。日期和种子在生成前已冻结。

这些是同一个公开电网上的新随机时序，能够检验对未用于本地开发的时序的表现。它们不构成第二电网，也不代表真实生产运行。原控制实验运行环境未改变；生成器依赖存放在独立D盘目录。

先检查全部场景的格式、输入哈希、静态电网配置、有限数值、初始环境读取以及生成器自身的损耗平衡检查。不依据控制器成绩删除场景或更换种子。官方生成器的预测修正失败计数也完整保留。

## 二、比较什么

| 方法 | 作用 |
|---|---|
| FULL | 完整候选查询参照 |
| CONTEXT_GATE | 当前冻结的条件核查版FRAME |
| FRAME_GUARD | 始终执行核查，检查门控省去了什么 |
| RANDOM_GATE0 | 相同前缀安全条件、相同支持范围守卫，随机跳过核查 |
| RANDOM_GATE1 | 第二个预先固定的随机门控种子，全部保留 |

随机跳过概率为4/13：旧校准集有14个安全状态，其中13个落在模型支持范围内，当前门控跳过4个。两随机臂在范围外都执行核查；范围内以4/13概率跳过。随机数只由固定种子和决策时已可见的前缀/上下文生成，不读取未来查询或教师标签。它匹配的是校准集上的期望跳过比例，不会事后强行匹配测试查询总数。

六场景×五方法×两次反向顺序计时，共60条串行回放。两次计时用于观察时间波动，两个随机种子用于保留随机规则差异，都不算额外独立日期。计时阶段不安装依赖、不训练、不启动第二个实验运行器。

## 三、量化指标与判据

1. 质量：不早于同场景FULL终止；双方完成时，完整周成本不超过FULL的0.5%。所有提前失败都报告。
2. 查询：只在相同时域且参照确实启动搜索的场景计算查询降幅，避免用更早失败换取表面节省。
3. 实际计算：先在每场景内平均两次控制时间，再计算场景相对降幅的宏平均；另列汇总秒数、P95及优化/预测/搜索管理的分解。
4. 新场景联合筛查：六场景质量均通过，查询宏平均减少至少50%，控制时间宏平均减少至少5%，至少4/6场景时间改善，且两次计时重复的宏平均均为正。
5. 识别价值：分别对两个随机种子判断。当前门控必须全部通过质量；若随机门控出现质量失败，或双方质量均通过且当前门控在至少4/6场景减少查询、查询宏平均至少少5%，则保留对应识别增量信号。否则报告尚未建立该增量。

这些是本轮冻结的投资筛查规则，不是显著性、等价性或一般质量保证。未通过时不自动调参、换日期或选择表现好的随机种子。
